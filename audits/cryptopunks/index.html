CryptoPunksMarket security audit

Audit by David Ryan using Codex (GPT-5.6 Sol High)
2026‑10‑28 against block 26,291,046
Contract on Ethereum mainnet: CryptoPunksMarket

CryptoPunksMarket is the immutable contract that records ownership and runs the original marketplace for the 10,000 CryptoPunks. It was deployed in June 2017, before ERC-721 existed, so its ownership, transfer, bid and sale interfaces are unique to this collection.

This review found no exploitable vulnerability. Its ETH balance matched all pending withdrawals and active bids exactly, to the wei. One medium integration hazard and two low defects remain for callers and event consumers to handle.

How this audit was made

I commissioned this independent audit from Codex. It read the deployed bytecode, the verified source and mainnet state at one pinned block. The report records the commands, evidence and limits so that its results can be checked.

Summary

CryptoPunksMarket holds no exploitable vulnerability. Its ETH liabilities reconcile exactly, its owner powers are inert, and its unchecked arithmetic is safe under the contract's fixed bounds.

One Medium integration hazard remains. Both withdrawal paths use Solidity's transfer, so they forward only 2300 gas. A recipient contract with an expensive receive path can never collect its own ETH.

Two Low defects affect live state or event consumers. A zero-address transfer has stranded a 0.02 ETH bid on Punk 685. Accepted bids also emit a PunkBought event with a zero value and zero buyer.

Three Informational findings cover the non-standard interface, market ordering and a historical owner-only counter weakness that is now unreachable.

The contract is immutable. Integrators must handle these behaviours at their own boundary.

Method

I pinned one Ethereum block before reading state. I then read runtime code, proxy slots, ordinary storage, public getters and ETH balances from that block.

The opcode walker strips the 43-byte metadata trailer before decoding. Its executable sweep found no upgrade or destruction opcode. All 27 dispatcher selectors match the verified ABI.

The source came from the explorer verification record. Larva Labs' archival build independently confirms that the published source compiles byte-for-byte to the deployed program. The GitHub source therefore does not differ from the deployed source.

I swept all 10,000 punkBids entries. I built the withdrawal address universe from 96,165 bid events and 30,638 sale events in the official CryptoPunks history API. Their bidder, seller and buyer fields produced 13,413 unique addresses.

Those event roles cover every route into pendingWithdrawals. The routes are sale proceeds, displaced bids, and a bid refunded when its bidder receives the punk. I then swept pendingWithdrawals for all 13,413 addresses.

tools/probe.py logs was attempted first. Blockscout returned HTTP 429 before the historical scan completed. The official history supplied the same event roles without depending on that rate-limited explorer route.

Prior work changed two checks. Etherscan lists a DTF audit dated 2021-09-02, but its linked report was unavailable during this review. The NFTX incident post-mortem describes a 2021 integration loss involving directed Punk offers. The deployed source confirms that the loss sat in the recipient vault's caller accounting, outside this contract.

The Medium issue is explicit in the public source and supplies no attacker method. It therefore does not require a private vulnerability embargo.

Findings

M-1 · Withdrawals forward only 2300 gas Medium

Priced exposure. The known amount lost through this cause is 0 ETH. The gross balance that can pass through these payout paths is 3,145.133320691470851579 ETH, or $7,432,453.26. This excludes the independently stranded 0.02 ETH bid in L-1.

withdraw() clears pendingWithdrawals[msg.sender], then uses msg.sender.transfer(amount). withdrawBidForPunk() clears the bid, then uses the same transfer primitive. Each call forwards exactly 2300 gas.

A recipient contract whose receive path exceeds 2300 gas cannot collect its ETH. The transfer reverts, so Ethereum restores the cleared state. The funds remain recorded, but only that same address may retry.

The bid path has the same problem. An outbid contract receives a pending withdrawal. A contract withdrawing its live bid receives a direct 2300-gas transfer. Neither route lets it nominate another recipient.

Gas repricing can create this failure after an integration launches. A fixed stipend that worked before Istanbul may fail after an opcode repricing.

Mitigation. A contract bidder or seller must expose a receive path that fits inside 2300 gas. Otherwise, use a thin receiver that can forward later.

L-1 · A zero-address transfer can strand an active bid Low

Priced exposure. Punk 685 has a stranded bid of 0.02 ETH, or $47.26.

transferPunk() accepts the zero address. It clears any sale offer but leaves an unrelated bid in place. withdrawBidForPunk() then rejects the withdrawal because it requires the punk owner to be non-zero.

The live state proves this sequence matters. Punk 685 has owner 0x0000000000000000000000000000000000000000 and an active 0.02 ETH bid from 0x8e4237fd48bbb843683c93bacad6a6966c9e9883. That bidder now carries 23 bytes of account code, but the owner guard fails before payout behaviour matters.

No owner can accept the bid, and the bidder cannot withdraw it. No function can restore a punk from the zero address. The 0.02 ETH is permanently locked.

Mitigation. Treat the zero address as a destructive burn. Never transfer a punk there while any bid exists. A caller should withdraw its bid before a known burn, although it cannot force the owner to wait.

L-2 · Accepted-bid events record zero value and zero buyer Low

Priced exposure. The direct value at risk is 0 ETH, or $0. Ownership and seller credit remain correct.

acceptBidForPunk() creates a local storage reference named bid. It copies bid.value into amount, clears the stored bid, and credits the seller with amount. It then emits PunkBought from the cleared storage reference.

The resulting event records value = 0 and a zero buyer. Transaction 0xc3a763…ddf66 accepted a 62 ETH bid for Punk 3960 at block 15,390,973. Its Transfer event names the real buyer. Its PunkBought event reports zero for both fields.

The misreported 62 ETH would equal $146,515.92 at this review's exchange rate. The seller still received the correct 62 ETH credit.

Indexers cannot treat every PunkBought event as authoritative. They must identify an accepted bid from the transaction call and preceding bid state.

The other events carry the values used by their state change. Ordinary buyPunk calls also emit a correct PunkBought event.

Mitigation. Reconcile accepted-bid events against Transfer, transaction input and storage history. Keep ordinary buyPunk events on a separate path.

I-1 · The interface is ERC-20-shaped but represents unique punks Info

Priced exposure. This causes no direct loss within the contract: 0 ETH. Downstream accounting can still be wrong.

The contract exposes name, symbol, decimals, totalSupply, balanceOf and an ERC-20-shaped Transfer. It has no ERC-20 transfer, allowance or transferFrom function.

It also has no ERC-721 ownerOf, approval, safeTransferFrom, tokenURI or ERC-165 support. Ownership lives in punkIndexToAddress(index).

The ERC-20-shaped Transfer carries the value 1, not the punk index. A generic event consumer learns that an account count changed, but not which punk moved. PunkTransfer supplies the index for manual transfers. Purchases instead rely on PunkBought, which has the accepted-bid defect above.

I-2 · Market ordering requires caller-side protection Info

Priced exposure. The contract cannot take more than the ETH a caller submits. The exposed amount is therefore the caller-authorised purchase price or bid, with no additional protocol balance at risk.

A public fixed-price offer goes to the first valid buyPunk transaction. Another buyer can move ahead in the mempool. Later buyers revert after the ownership or offer checks fail.

A private offer enforces onlySellTo == msg.sender. An outsider cannot buy it directly. A recipient contract can reintroduce a race if it credits its own external caller without checking the punk owner. NFTX documented a 6 ETH loss from that downstream mistake in 2021.

buyPunk treats the offer value as a minimum. It credits the seller with all of msg.value and refunds no excess. Buyers should send the exact price that they intend to pay.

Bid acceptance uses the seller's minPrice. A lower bid reverts. A bidder can withdraw or replace a bid only with a higher value, so a mempool observer cannot lower the seller's settlement.

I-3 · The initial assignment counter could underflow before finalisation Info

Priced exposure. The live path exposes 0 ETH. Assignment is closed, and the owner cannot reach the affected subtraction.

Before finalisation, setInitialOwner did not preserve its remaining-count invariant when the owner reassigned a punk to the zero address. That operation decremented the old holder, assigned zero, and did not increment punksRemainingToAssign.

A later reassignment from zero treated the same punk as newly assigned and decremented the counter again. Repeating the sequence could make the counter reach zero early or wrap below zero.

The weakness required the trusted owner and only affected initial assignment. allPunksAssigned is now true, so setInitialOwner reverts before this code. The current assignment flag is true, and its remaining counter is zero.

Stale offers and bids

The state transitions are internally consistent.

  • A manual transfer clears its sale offer. Any unrelated bid remains live.
  • If the recipient is the bidder, the transfer clears that bid and credits its value to the recipient's pending withdrawal.
  • buyPunk clears the offer. An unrelated bid remains live.
  • If the buyer is the bidder, buyPunk clears and refunds that bid through pendingWithdrawals.
  • acceptBidForPunk clears both the sale offer and the accepted bid.

At the pinned block, four active bids also had open sale offers. Punks 1930, 4202, 5170 and 6938 had offers of 32.980711, 40, 65 and 32.97 ETH. Their bids were 0.01, 38, 45 and 30.5 ETH. This confirms that unrelated offers and bids coexist as the source specifies.

Ordering and reentrancy

buyPunk changes ownership and balances, clears the offer, and credits the seller. It then clears a bid from the buyer, if one exists. It makes no external call.

acceptBidForPunk changes ownership and balances, clears the offer, snapshots the bid value, clears the bid, and credits the seller. It makes no external call.

enterBidForPunk credits the displaced bidder before replacing the bid. The credit is an internal accounting write, with no external call.

withdraw snapshots the credit and writes zero before transferring ETH. withdrawBidForPunk snapshots and clears the bid before transferring ETH. Each transfer forwards 2300 gas. A failed transfer reverts the whole call, so Ethereum restores the earlier state.

These sequences follow checks-effects-interactions. Reentrancy cannot observe an uncleared withdrawal or bid, and the stipend prevents a useful stateful callback. The fixed stipend creates M-1 instead.

What the contract cannot do

  • It cannot upgrade, delegate execution, deploy another contract or destroy itself.
  • It cannot pause transfers, sales, bids or withdrawals.
  • It cannot mint more than 10,000 punks.
  • Its owner cannot assign or reassign a punk now.
  • It cannot seize a punk, change a bid, set a fee or redirect a withdrawal.
  • It cannot recover a punk or ETH sent into an unreachable state.
  • It cannot choose arbitrary call targets or calldata. Its external value transfers are the two fixed-stipend withdrawal paths.

The stored owner is the original deployer. Three functions check that address.

Owner-gated function Present effect
setInitialOwner Always reverts because allPunksAssigned is true
setInitialOwners Any non-empty call reaches setInitialOwner and reverts; an empty call changes nothing
allInitialOwnersAssigned Can only write true over the existing true value

No function changes owner. The remaining owner authority is inert.

Why 2017 arithmetic is safe here

Solidity 0.4.11 does not check overflow or underflow. This contract uses no SafeMath, so each arithmetic operation needs its own bound.

setInitialOwner safely decrements an old holder's balance because that holder owns the punk. Its remaining-count decrement did have the owner-only weakness described in I-3. The whole function is now dead because assignment has closed.

getPunk checks that assignments are complete, that a punk is unowned, and that the remaining count is non-zero. The live remaining count is zero, so this path is also dead.

Every market transfer decrements the current owner's balanceOf. Ownership of that punk proves the balance is at least one. No subtraction can underflow.

Each balanceOf increment is bounded by the fixed supply of 10,000. No account can approach the uint256 limit.

nextPunkIndexToAssign is never modified after its zero initialisation. totalSupply is written once as 10,000. The setInitialOwners loop counter is bounded by calldata length and transaction gas, far below 2^256 iterations.

Every bid value comes directly from msg.value. A replacement must exceed the stored bid, and the displaced value moves unchanged into a withdrawal credit.

Each pendingWithdrawals addition is backed by ETH already held in the contract. Overflow would require almost 2^256 wei. Ethereum's total supply is many orders of magnitude lower.

The exact solvency reconciliation corroborates these invariants. No unchecked operation has created or erased a wei of liability.

Compiler risk

The verified build used solc 0.4.11 with the optimiser enabled for 200 runs. The Solidity project lists 19 known bugs for that exact release. None intersects this source.

The contract has no memory byte deletion or mutable storage array operations. It never resizes its stored strings. It also has no signed arrays, function pointers, inheritance, libraries, exponentiation, delegatecall, ecrecover, nested array decoding or empty-string external calls. These facts clear 16 entries.

ImplicitConstructorCallvalueCheck requires a missing constructor and an inherited constructor. This contract has an explicit payable constructor and no inheritance.

KeccakCaching affects optimiser reuse of hashes with equal rounded memory contents but different lengths. The source has no inline assembly. Its compiler-generated mapping hashes always use fixed, full-word inputs.

ZeroFunctionSelector does not apply. All 27 dispatched selectors are non-zero, and the contract defines no payable fallback.

Integration checklist

  1. Read ownership from punkIndexToAddress(index). Do not call ERC-721 ownerOf.
  2. Use the punk index in PunkTransfer, PunkBought or Assign. The ERC-20-shaped Transfer value is always one.
  3. Reconstruct accepted bids from transaction input, Transfer and bid state. Their PunkBought value and buyer are zero.
  4. Send the exact intended price to buyPunk. Excess ETH goes to the seller.
  5. Treat public listings as first-transaction-wins. Use a directed offer when a specific buyer must receive the punk.
  6. A recipient contract must bind its external caller to the punk owner before it consumes a directed offer. The native onlySellTo check is insufficient for the recipient's own accounting.
  7. Keep any withdrawal receive path below 2300 gas. The contract cannot pay a different address.
  8. Check for a live bid before any zero-address transfer. The bid can become permanently unreachable.
  9. Use an ERC-721 wrapper when an integration requires approvals, safe transfers or ERC-165. The legacy WrappedPunks contract is 0xb7F7F6C52F2e2fdb1963Eab30438024864c313F6. The later CryptoPunks721 wrapper is 0x000000000000003607fce1aC9E043a86675C5C2F.
  10. Read images and attributes from the sealed 2021 data contract at 0x16F5A35647D6F03D5D3da7b35409D65ba03aF3B2. They are not stored here.

Do not confuse this contract with the earlier deployment at 0x6Ba6f2207e343923BA692e5Cae646Fb0F566DB8D. The earlier address still has 4,131 bytes of runtime code onchain. Larva Labs states that its purchase path allocated sale funds to the buyer instead of the seller. CryptoPunksMarket is the replacement reviewed here and does not carry that error.

Limits of this review

  • The scope is the single CryptoPunksMarket address. The earlier contract, wrappers, data contract, websites and downstream protocols were not audited.
  • This was a manual source, bytecode and live-state review. It did not include formal verification, symbolic execution or fuzzing.
  • The withdrawal address universe came from the official event history after Blockscout rate-limited the raw log scan. The 13,413-address state sweep itself completed without an error.
  • The Medium finding states gross custody exposure. This review did not prove which of the 816 current creditors have receive code exceeding 2300 gas.
  • State and USD values move after block 26,291,046.
